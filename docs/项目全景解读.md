## 0. 一句话版本

一个跑在你自己机器上的 AI 伴侣：记得住上周说过的话，有自己的心情曲线，会在你走开半小时后自己写日记，能打电话。数据全在本地一个 `storage/` 目录里。

真正值得注意的是：**这个项目一半以上的代码是兜底和降级**。不是"能跑就行"的 demo，而是"每一步都可能失败，失败也要保持角色人设"的工程。这个判断贯穿全文，面试时也值得挂在嘴上。

## 1. 它解决的问题，和它的设计信条（含不好听的那部分）

问题很直白：大多数 AI 伴侣是"无状态请求-响应"。秒回、全知、上句不接下句、记不住你上周说过什么。这不是模型的锅，是架构的锅。

Aria 的应对是把"人的时间性"做成结构体，而不是形容词：

| 机器感从哪来 | 用哪个结构把它顶回去 |
|---|---|
| 每次从零开始 | 短期会话管家 + SQLite 硬事实档案 + Chroma 长期记忆 + 软画像，四层 |
| 情绪是识别出的标签、下一句就忘 | `MoodEngine` 心情状态机，随轮次漂移、跟着关系数值落库 |
| 全知全对永不犯错 | 工具会失败；失败了用符合人设的兜底话承认，不编答案 |
| 永远等你开口 | `IdleDiaryWatcher` 后台巡检，闲置 30 分钟自动写当天日记 |
| 人设铁板一块 | 稳定内核（人设正文 + taboos）+ 波动表层（心情 + 小动作骰子 + 关系阶段） |
| 模型想说啥就说啥 | 输入黑名单预检 + 句级输出审核 + 单字崩拦截 |

**ARCHITECTURE.md 里那句"像人靠架构，不靠提示词"要诚实看待。**

这句话是设计主张，不是事实描述。翻 `data/persona_config.json` 第 7 行，`background_story` 是一段约 800 字的角色设定正文（身份、性格内核、喜好、雷点、说话风格），`PersonaEngine.compose()` 每轮都把它整段拼进 system prompt（`capability/persona_engine.py:40`）。加上 taboos、mode_tones、diary_notes、fallback_replies、ask_templates，这个项目**极度依赖提示词**。

所以准确的说法是：**"靠架构提供能力，靠提示词表现角色"**。架构负责"真的记得住、真的会漂移、真的会失败"这些无法靠措辞实现的部分；提示词负责"说出来像不像这个人"。两者分工明确——这也正是"换人设只改一个 JSON、代码一行不用动"能成立的原因：角色相关的措辞全部收进了配置，能力相关的机制全部留在代码。

如果面试官问"那你的'不靠提示词'是不是自我矛盾"，这就是答案。别绕，承认张力反而显得想明白了。

## 2. 分层与依赖规矩

```
interaction/    Web 入口：REST/WS 路由、消息网关、语音流收发、Gradio 兜底页
    ↓
orchestration/  调度：对话主流程管道、轮次取消、语音路由决策、缺信息追问、异常降级
    ↓
capability/     智能：感知、记忆、人设组装、回复生成、日记、工具编排、随机小动作
    ↓
tools/          纯技术封装：LLM 客户端、语音 SDK、外部 API、存储门面、日志、证书
    ↓
data/           纯存储：SQLite + Chroma + persona_config.json

shared/   层间契约（types.py）+ 全局单例注册表（singletons.py）
config/   环境变量与业务配置的读取
bootstrap.py    组合根
```

规矩只有一条：**只许向下调用**。跨层传的数据定死在 `shared/types.py`（`MemoryBundle` L18 / `PromptPackage` L63 / `FinalReply` L72 / `InputMessage` L81），字段名就是契约。

**组合根为什么单独抽出来。** 原来服务装配懒加载藏在 `shared/singletons.py` 里，结果是 registry 必须 import tools 和 capability 的具体实现——`shared` 反向依赖了上层，分层直接破掉，而且出现"import 一下就产生副作用（偷偷建 Chroma 客户端）"。

现在 `bootstrap.py` 是全项目唯一允许"知道所有层的存在"的文件。它 import 具体实现、建实例、注册进 `services`；`shared/singletons.py` 退化成纯注册表（只有 dict + `get/mark_error`，不 import 任何上层）。装配时机也变明确了：`main.py:41-52` 的 lifespan 里调一次，别的任何时刻都不装。

好处是：`shared` 不再反向依赖上层，import 不产生副作用，装配时机一眼可见（grep `bootstrap()` 就到）。

两个真正的单例，别到处 new：

- `KEEPER`（`orchestration/pipeline.py:67`）——短期记忆管家。管道要读上下文、writeback 要写记录，必须是同一对象；realtime 语音写回也 import 它（`interaction/api.py:108`），所以打字聊天和语音电话共用同一段上下文。
- `services`（`shared/singletons.py:38`）——服务注册表。单个服务初始化失败只记账不抛出（bootstrap 里每个 `try/except` 都配 `services.mark_error`），语音 key 没配照样能文字聊天。

## 3. 一轮对话的完整链路

主流程是 `orchestration/pipeline.py` 的 `DialoguePipeline`。

**核心事实：`astream()` 是唯一实现（L454），`handle()` 是它的消费者（L399）。** 非流式接口 `/api/chat/send` 和 Gradio `/ui` 没有自己的第二套代码，只是把事件收起来重拼成 `FinalReply`——包括把 `<voice>` 标签重新包回去（L442-445），好让下游 `renderer.render` 照旧去剥标签 + 合成语音。这个设计的价值是"不可能漂移"：改了流式逻辑，非流式一定跟着变。

### 流式版（`POST /api/chat/stream`）

| # | 步骤 | 位置 | 干什么 | 产出/事件 |
|---|---|---|---|---|
| 0 | 恢复短期记忆 | L467 | `KEEPER.restore()`，有缓存就立刻返回 | — |
| 0 | 开轮 | L474 | `TURN_REGISTRY.start(session_id)`，会先取消这个会话的旧活跃轮 | `start{turn_id}` |
| ① | 安全预检 | L488 / L727 | `SafetyReviewer.review(text, "input")`，黑名单子串匹配 | 不过 → `refuse` + `done`，**return，不写回** |
| ② | 感知 | L498 / L733 | 意图+情绪（一次 LLM）**∥** 记忆召回（两次向量检索），ThreadPoolExecutor 两线程并行 | — |
| ②' | 分流 | L502 | `intent in ("weather","search","image","diary")` → 工具链，否则人设链 | — |
| ③a | 工具链 | L656 | `toolcall`（三级降级）→ 若无 final_reply 则 `respond`（转述成人话）→ 走装配器 | `sentence`/`voice` |
| ③b | 人设链 | L511 + L558 | `compose` 拼提示词 → `llm.astream_chat` 流式 → 每 chunk 喂 `_ReplyStreamer` | `emotion`/`sentence`/`voice` |
| ③' | 句子出口 | L689 / L701 | 每句 / 每段 `<voice>` **先审后推** | 不过 → 抛 `_ReviewReject` |
| ④ | 记忆写回 | L521 / L813 | 短期记忆、chat_log、硬事实蒸馏、亲密度、心情、画像 | — |
| ⑤ | 语音兜底 | L525 | 用户点名要语音但整轮没 `<voice>` → 用已推正文补一条 | `voice` |
| ⑥ | 图片 | L537 | `output_mode=="image"` 补一条 | `image` |
| ⑦ | 收尾 | L540 | `done{full_text, output_mode, image_path}` | `done` |

异常出口四种，全部回到事件层面，不漏到 HTTP：

| 异常 | 位置 | 事件 |
|---|---|---|
| `TurnCancelled` | L546 | `cancelled{reason:"superseded"}`，**什么都不写** |
| `_RefuseTurn` | L549 | `refuse{replace:true}` + `done` |
| 其他 Exception | L552 | `error{code:"pipeline_error"}` |
| 正常结束 | L555 | `finally` 里 `TURN_REGISTRY.finish` 登出 |

### `_ReplyStreamer`：流式装配器（`pipeline.py:217`）

一个纯逻辑类，不碰 I/O。干三件事：

1. **情绪前缀**（仅语音轮）：扣住开头 ≤24 字解析 `[情绪]（语气）`。词不在 `EMOTION_WORDS` 白名单就整个当正文。`(语气)` 的右括号没来就继续等，攒到 24 字强制裁决（L249-276）。
2. **`<voice>` 状态机**：`_split_tail`（L280）只扣住"不完整的标签前缀"（比固定扣 8 字准），保证 `</voice` 这种半截永远不会当正文推出去。`finish()` 里模型忘了闭合就把攒的当语音处理，不丢（L378-382）。
3. **句子切分 + 首句短缓冲**：遇 `。！？；\n` 切句（L91），无标点长文本到 60 字强切（L93）。首句实质字符 ≤4（`_FIRST_HOLD_MAX` L95）先扣住等下一句，避免"嗨，"、"好。"单独占一个气泡。

产出三元组：`("emotion", 词, 描述)` / `("sentence", 文本)` / `("voice", 文本)`，以及 `finish()` 才可能有的 `("held", 文本)`。

### 非流式的复用关系

```
/api/chat/send                        /api/chat/stream
      ↓                                      ↓
DialoguePipeline.handle()            DialoguePipeline.astream()
      ↓ 内部 await astream(...)，synthesize_voice=False          ↓ 直接消费
重拼 FinalReply（含 <voice> 原文）     逐帧 SSE
      ↓                                      ↓
renderer.render 剥标签 + 合成          事件内有 audio_b64 现成
```

`handle()` 里有一点值得记住：收到 `cancelled` 时它返回 `FinalReply(text="")`（L437-439）——因为旧同步路径从来没被取消过，这里不能把取消当成异常兜底话说给用户听。

### 取消：为什么这套东西存在

`orchestration/cancellation.py` 维护一条不变式：**每个 session 同一时刻最多一个活跃轮**（L51-59，`start` 时自动取消上一个）。

- 句柄用 `threading.Event` 而非 `asyncio.Event`（L28）：管道里有大量 `await asyncio.to_thread(...)`，取消状态要能被另一个线程读到。
- 检查点是协作式的，插在四个地方：感知/分流之后（L489/499/520/522）、每个 token 之后（L573）、推每句之前（L694）、writeback 每个子步骤之前（L816-893）。
- `finish()` 在 `finally`（L555），登记不会泄漏。

之所以必须是"会话级单轮不变式"而不是"客户端乖乖先 cancel 再发"：前端的打断路径是"立刻取消本地 + 立刻发新消息"，两条请求在服务端顺序不保证。让 `start` 自己去取消旧轮，时序竞态就没了。

## 4. 记忆系统

四层，各管一件事：

| 层 | 实现 | 存哪 | 生命周期 |
|---|---|---|---|
| 短期记忆 | `SessionMemoryKeeper` | 内存 + SQLite chat_log | 最近 12 轮，超了压成摘要 |
| 硬事实档案 | `ProfileUpdater` | SQLite `profile` | 永久，10 个白名单字段 |
| 长期记忆 | `ConversationDistiller` | Chroma `distilled_memory` | 永久，带 importance 1~5 |
| 软画像 | `PortraitBuilder` | SQLite `portrait` | 标签 14 天不出现就清掉 |

**防污染是这个子系统里最重要的一条。** 硬事实入库只有一条通道 `apply_fact()`（`memory.py:343`），正则抽取和 LLM 抽取都汇到这里：

- 值没变 → 一条记忆都不加，直接 return（L354-355）。消灭"用户叫小明"入库八遍。
- 值变了 → 连同改口一起记："用户把住在从 A 改成了 B，以新的为准"（L359-365）。
- 正则带否定防护（L335-341）：匹配点前两个字内有"不/没/别/未"就不收，"我不叫小明"不会变成事实。
- LLM 抽取（`PortraitBuilder.refresh`）带 confidence 门槛，默认 0.6，低于不入库（L249）。
- 画像标签 `tag_updated` 记每个标签最后被提到的时刻，超 `persona_decay_days`（14 天）自动清除（L284-313）。

 `SessionMemoryKeeper` 有两个细节本科生容易漏：

- 锁内只做字典操作，LLM 摘要一律放锁外（L67-70）。持锁调模型会把所有会话串行化，比不加锁还糟。
- 会话上限 8 + LRU 淘汰（L42-48）。多会话长跑时内存不会只增不减，代价是第 9 个会话进来时最久未碰的那份上下文会被摘掉（下轮 `restore` 再从库里读回来）。

**日记**是角色的自传，`DiaryWriter`（`capability/diary.py:15`）：

- id 是 `diary-YYYY-MM-DD`，同天重写即覆盖（L113-124）。
- 日期取"最后一条聊天记录的日期"而不是今天（L42-44）——闲置触发经常跨零点，23:50 聊完、00:20 才触发。
- 超 30 篇自动翻最旧的（L131-137）。
- **触发入口有两个**：用户说"写日记"（走 `diary_write` 工具 → `_run_native_loop`）和 `IdleDiaryWatcher` 后台巡检（每 60 秒点名一次，谁闲够 30 分钟还没写当天日记就补一篇，`capability/proactive.py:52-76`）。巡检用 `_done` 集合 + `skip_if_exists` 双重防重写——进程重启后 `_done` 清零，但日记在册就直接跳过，不会白烧模型调用。

## 5. 人设：身份（提示词）与状态（机制）的分工

| 部分 | 在哪 | 性质 |
|---|---|---|
| 身份 + 说话方式 | `data/persona_config.json` | 静态，每轮整段进 system prompt |
| 此刻的心情 | `MoodEngine`（`quirks.py:26`） | 每轮 30% 概率在情绪池漂一格，跟着关系数值落库 |
| 这一轮皮不皮 | `QuirkDirector`（`quirks.py:56`） | `quirk_rate` 0.12 掷一次骰子 |
| 说话分寸 | 关系阶段/亲密度（`RelationshipTracker`） | 累计生成，回喂 compose |
| 周期鲜味 | `ClockTool.time_guidance()` | 按时段给一句"现在说什么得体" |

几个断言要有理有据：

- **安抚/危机轮，随机性全部收起。** `MoodEngine.update` 强制返回"心软"（L38-39），`QuirkDirector.roll` 直接返回空串（L66-67）。理由不是"这时候应该稳重"，而是"这时候还在表演性格就是事故"——喜剧节奏崩了下一轮可以重来，对方崩溃时戏弄了人没法撤回。
- **撒娇有亲密度门槛**（`_CLINGY_INTIMACY=20`, L88）。刚认识就撒娇是油腻，不是可爱。
- **小动作依赖素材存在与否**（L82-89）：没有缺点记录就没有"调侃"这个动作，没有长期记忆就没有"提旧事"。自动缺席，而不是让模型对着空气编。
- **每条指令都写"只此一次"**（L101-133），防止皮个没完。

值得注意的一点：`data/schemas.py` 里 `PersonaConfig` 有 `self_introduction / age / hobbies / daily_reset / memory_config` 五个字段，`PersonaConfigStore` 会读（L44-52）但代码里**没有任何地方消费**（我 grep 过）。它们目前是"给人看的配置说明"，不是运行时参数。面试时如果被问可以主动说，显得你连没用的字段都知道在哪。

## 6. 语音三链路

| 路由 | 链路 | 经过对话管道吗 | 输出审核 | 延迟 | 记忆 |
|---|---|---|---|---|---|
| `cascade` | ASR → **走完整管道** → TTS | 是（默认路由） | 有 | 最慢，三段网络相加 | 完整共享 KEEPER |
| `e2e` | 录音 → `SpeechDialogEngine`（`skills.py:38`） | 否 | **没有** | 中 | 单轮感知 + 写回，无 compose/quirk |
| `realtime` | WebSocket 直连 Omni 多模态模型 | 否 | **没有**（模型侧管） | 最快 | 开场白注入 + 每轮写回 |

切换是热的（`VoiceRouteManager.switch`），不清上下文不清亲密度。连续失败 2 次自动降回 cascade（`_FAIL_LIMIT=2`，`managers.py:22`）——cascade 最慢但一定不出事。

**为什么不做成一条：** 三条链路的取舍轴完全不同，合并就必须在"最慢的可靠性"和"最快的延迟"之间做妥协。分开+热切换+自动降级，用户默认拿到可靠的，想要速度自己切。

**e2e 没有输出审核是真缺口**，我在第 7 节老实写。

**音频格式铁律**（踩过坑的）：
- 前端 WebAudio 固定采 16kHz 单声道裸 PCM16，不用 MediaRecorder（webm 容器后端吃不下）。
- 采集处理图**建一次常驻**，只靠 `recording` 标志丢数据（`index.html:1077`）。Chrome 只在有消费者时保持麦克风打开，反复拆图会让蓝牙耳机在 HFP/A2DP 之间反复协商断连。
- 裸 PCM 进 ASR 前包 WAV 头（`speech.py:51`）；realtime 回程 24k 裸 PCM 同样包 WAV 再下发（`realtime.py:229`）；TTS 回 mp3。前端按 RIFF 魔数区分。
- 回程音频必须从用户手势解锁的 AudioContext 播（`index.html:996`）。手机自动播放策略会**静默**拒绝非手势时机的播放，表现为"通话有字没声"。

**情绪标注协议**：语音轮回复开头带 `[开心]（压低声音）`，这是给 TTS 的 instruction。合成前`strip_emotion_marks` 剥掉，标记不进展文本也不进聊天记录。`split_emotion` 只用"开头第一个 + 白名单 + 紧邻"三条约束（`speech.py:46-48`），这是修 bug 修出来的：早先用宽正则，会把正文里"第[1]点"的方括号和"他（我朋友）"的括号也当标记剥掉。

## 7. 兜底与降级全景

这是比重最大的一块。

### LLM 层（`tools/llm_client.py`）

| 环节 | 做法 | 位置 |
|---|---|---|
| 熔断打开 | 连续失败 ≥2 次（`max_errors`）记 `_opened_at = monotonic()` | L105-107 |
| 冷却窗 | 120 秒内（`cooldown_seconds`）**完全不碰主模型**，直接走备用 | L79-82 |
| 半开探测 | 冷却到期后下一次调用走主模型，但传 5 秒短超时（`probe_timeout_seconds`） | L88-93 |
| 成功闭合 | 清空 `_error_count`、清 `_opened_at` | L97-98 |
| 备用参数 | GLM 系是"始终思考"模型，摘掉 `enable_thinking`，换 `thinking_effort: low` | L112-115 |
| 两台都挂 | 抛 RuntimeError 带两个错误，上层接兜底话 | L120 |

为什么熔断**按时间窗**但探测用**5 秒短超时**：两者要解决的问题不同。冷却窗是为了"别在明确坏掉的服务上浪费 60 秒超时"；而半开探测本身是一次赌注，赌错的成本必须小——用默认的 60 秒去探测，等于每条消息都要白等一分钟，聊天直接不可用。5 秒够判定网络通不通、key 有没有失效。

为什么同步路径和流式路径共用同一套 `_opened_at/_error_count/_cooldown`（`astream_chat` 注释明说了，L179-180）：不共用就变成两套状态机，一个模型"半恢复"的时候会出现同步觉得能用了流式觉得不能用的分裂状态。

流式降级有硬约束（L220-239）：**只能在还没吐出任何 token 之前换备用**。已经 yield 过再换也是接不上的半截话，那种情况直接抛，由上层收尾。

### 工具调用三级降级（`capability/toolcall.py`）

| 级 | 条件 | 做法 |
|---|---|---|
| L1 | `llm_supports_tool_call=true` | 模型原生 function calling，最多 4 轮循环，工具结果回填喂回去继续生成 |
| L2 | L1 抛异常 | 让模型文本规划出 `{tool_name, arguments}`（JSON），代码自己执行，结果交给 `persona_wrap` 转述 |
| L3 | L2 也挂 | `RULE_TOOL_MAP` 硬编码 + 正则抠参数，模型再怎么抽风都有底 |

L1 循环里还有一个容易被忽略的点：`should_cancel` 是调用方注入的"该不该停"回调（L122、L184-185），能力层不 import 调度层。这是为了让 capability → tools 的依赖方向不破。

### 流程层

| 场景 | 处理 |
|---|---|
| 输入黑名单 | 直接 `refuse`，不进模型，不写回 |
| 句级输出审核不过、还没推过 | 换干净说法重跑，与单字崩共用 `attempt` 计数，最多 2 次 |
| 句级输出审核不过、已经推过 | 整轮降级成兜底话（撤不回） |
| 单字崩（≤1 个实质字符） | 安全重写（一个 token 都没推，重写是安全的） |
| 缺城市 | 追问而不是瞎查默认城市（L783-785） |
| 主备模型都挂 / 中途断流 | 推过内容就按现有内容收尾；一个字都没推就退回 `generate()` 的兜底话整段重发 |
| 语音路由连续失败 2 次 | 自动降回 cascade |
| 语音合成失败 | 只回文字，前面的识别与生成不白干 |
| 日记写失败、画像更新失败、向量库挂 | 静默，聊天照常 |

### 数据层

- `storage.py` 的 `_read_json` 读坏了返回默认值而不是抛异常。
- `_KV_DISPATCH`（L274）未知的 store 返回 False 而不是崩。
- Chroma 建不起来时 `ChromaClient.available=False`，`ensure_ready` 直接 return，`search_*` 返回空列表。
- SQLite 单连接 + `threading.Lock`，WAL 模式，`check_same_thread=False`。

## 8. 关键设计取舍逐条

**为什么移除 LangGraph。** 原来的编排是一张状态图：一摊节点函数 + 一段建图接线。实际用下来图的全部能力只用到了三件事——顺序、分支、一个有界重写循环。而代价是：状态字典变成弱契约（拼错一个 key 不会报错，只会静默拿 None）、调试要额外理解 state graph 的语义、引入一个大而重的依赖（现在 `requirements.txt` 里已经没有 langgraph 了，我 grep 过全项目一个 import 都没有）。换成普通 async 方法 + if 分支后，控制流就是 Python 控制流，堆栈可读、断点可打。`ARCHITECTURE.md` 第 27 行的技术栈表已经更新成"普通 async 管道"，但第 71-94 行那张**流程图还没改**，仍然画着 LangGraph 时代的节点名。

**为什么句级审核。** 流式一旦首 token 出去就没有回头路。等整段生成完再审，那就不叫流式了。所以审核粒度必须下沉到"句"——每句过 `SafetyReviewer` 才推（L689）。代价在第 9 节老实讲。

**为什么取消之后什么都不写。** 这是偏离设计文档的有意选择，代码注释里写得很清楚（L813-824）：写任何东西都会让"这轮当没发生过"不彻底，而 chat_log 的两个用途（写日记、重启后恢复短期记忆）都不需要一条中途被丢弃的痕迹。文档里原本说"chat_log 可以补一条 cancelled 标记"，现在没这么做。而且 `TurnRegistry.start` 的会话级不变式让"取消但没被新轮接管"几乎不会出现——新轮会先取消旧轮。

**为什么情绪正则要收紧。** 见第 6 节：宽正则剥掉了正文里的方括号和普通括号。改成"只认开头 + 白名单词 + 紧邻"三条约束后，唯一可能的失败是模型把情绪标记写到中间，那种情况按正文念出来（可以接受，比毁掉正文便宜）。

**为什么打断要把旧消息折回合并请求。** 这是个产品判断，不是技术判断（`index.html:795-804`）。打断的正确语义是"我不想听你答这句"，不是"我那句话没说过"。如果只丢弃，用户就得把上一句重打一遍。所以 `send()` 把 `inFlight.texts` 接过来塞进合并窗口，和新打的这句一起发。**另外还有一个纯粹的技术理由**：连打三句时，不做合并就是 3 次 abort + 3 次请求；开了 500ms 合并窗口就变成"1 次白烧 + 1 次真请求"。500ms 约等于人说话的一拍，用户无感。

## 9. 有意的不对称（别当成 bug 修）

这几条面试时最容易被抓，全部背下来。

| # | 现象 | 为什么是有意的 |
|---|---|---|
| 1 | **工具链不做"审核不过就重写"**，只有人设链做（`_astream_tool` 注释，L657-659） | 工具链文本是工具结果拼装的，不是模型自由发挥。重写等于让模型再犯一次同样的错；直接整轮降级更干净，也不重跑工具（工具调用贵且有副作用） |
| 2 | **流式路径丢掉了部分整轮重写能力**（L23-27 的注释明说是一次"有意的能力下降"） | 规则是"还没推出任何内容 → 允许重写（最多 2 次）；推出过 → 只能整轮替换"。损失是：原来"整段生成 → 整段审核 → 重写 2 次 → 婉拒"的路径没了。换来的是首 token 一到就能开口说话。**这个取舍项目的作者是明确接受的，不是没发现** |
| 3 | **`call_id` 被丢弃**（`toolcall.py:206-224` 有一大段注释） | GLM 兼容接口不吃 `role:"tool"`，传过去直接报错，所以结果降级成一条 `role:"user"` 的普通文本回填。代价：模型看不出"这条结果对应哪次调用"，可能重复调同一工具；且 `chat_with_tools`（`llm_client.py:160`）只取 `tool_calls[0]`，模型一次想调多个工具时后面的会被丢掉。当前场景（单用户、一轮基本一个工具）够用。注释里写清了将来要改需要动的三处 |
| 4 | **KV 的 read/write 不对称**：`persona_config` 只在 read 表里，`write` 直接返回 False（`storage.py:266-282`） | `persona_config` 的正主是 `data/persona_config.json`，是给人改的，不该经运行时 KV 写入。同理 `image` 的 read 是"列出全部"、write 是"存一张"，两边语义本就不是一对。注释里写着"别顺手对齐成一样" |
| 5 | **e2e 和 realtime 两条语音链路没有本地输出审核** | 这条老实说我看不到"有意"的证据，更像是缺口。**cascade 走完整管道所以有审核；e2e（ `skills.py:69` 的 `_reply`）和 realtime（模型侧）都没有。** 如果被问，诚实答"这是当前缺口，两条路的输出只靠 taboos 提示词约束，没有代码层卡口" |
| 6 | **长期记忆检索不按 session 过滤** | 有意：跨设备的"同一个人"。代价是多会话场景记忆互相可见 |

### 关于"追问话术绕过输出审核"这条——我要更正一下

传下来的任务清单里说："`toolcall` 里缺城市时直接写 `final_reply` 然后去 writeback，同时跳过 respond 和 review"。

**我把当前代码读完了，这条现在不成立。** 缺城市那条（`_toolcall` L783-785）确实直接写 `state.final_reply` 并返回，但 `_astream_tool`（L665-673）后续会把 `state.final_reply` 喂进 `_ReplyStreamer`，再过 `_emit_frag` → `SafetyReviewer.review(text, "output")`（L689）。所以**追问文本现在是过输出审核的**。

这个是重构 C1b/C1c 的副产品：老 `graph.py` 里那条分支确实是绕过 review 的，改成统一走装配器之后顺手被补上了。如果面试官问，答"追问文本来自 `persona_config.json` 的人工配置，不含用户输入，所以历史上绕过也是可接受的；当前代码它其实也过审了"。

真正**仍然绕过**审核的出口是这三处，源头都不是模型自由生成：
- `FallbackController.fallback_reply()` 返回的兜底话（`managers.py:104`），源头是 `persona_config.fallback_replies` 或代码里的中性默认。
- `want_voice` 兜底（L525-534）：把**已经逐句审过**的 `display_parts` 拼起来补一条语音。
- e2e / realtime（上文第 5 条）。这个不一样，源头是模型。
